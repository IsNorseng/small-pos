# Руководство пользователя и разработчика

Небольшое бесплатное Android-приложение для кофейни, чебуречной или овощного киоска. Один APK, одно устройство, локальная SQLite-база. Без собственного сервера, аккаунта разработчика приложения и подписки.

**Состояние первой версии:** APK собирается и подписывается. Расчёты и целостность SQLite проверяются локальными тестами. Полный прогон Android-тестов и приём настоящего платежа Сбера ещё требуют проверки на подходящем устройстве и банковского API-доступа. До этого версию следует использовать для знакомства и тестирования, а не считать сертифицированной кассой.

## Установить и попробовать

1. Скачайте `small-pos.apk` со [страницы тестового релиза](https://github.com/IsNorseng/small-pos/releases/tag/v1.0.0-preview.1).
2. Откройте файл на Android **8.0 или новее**. Разрешите установку приложений этому источнику, если Android попросит.
3. Укажите название точки и **два разных PIN-кода по 6–12 цифр**: администратора и продавца.
4. Выберите готовый каталог: кофейня, овощи и фрукты, чебуречная; либо начните с пустого.
5. В «Товары и цены» измените примерные цены. В настройках выберите сценарий покупателя и способы оплаты.
6. Нажмите «Перейти к клиенту». Добавьте товары, оформите заказ, проверьте работу со стороны продавца.

Сохраните PIN администратора отдельно. Пароля по умолчанию и восстановления через интернет нет. Удаление приложения или очистка его данных удаляет базу; заранее сохраните резервную копию.

## Два сценария

**Кофейня / еда:** клиент выбирает товары → оплачивает → после подтверждения оплаты заказ попадает в «Оплаченные · к сборке» → продавец собирает и нажимает «Покупка выдана».

**Магазин:** клиент берёт товары → указывает их в корзине → оплачивает → после подтверждения оплаты покупка завершается. Отдельная выдача продавцом не требуется.

Оба сценария работают на **одном устройстве**, с переключением роли. Отдельный экран продавца на другом телефоне и синхронизация устройств в эту версию не входят.

Для овощей доступны цены за килограмм и ввод веса до грамма. По умолчанию вес вводит продавец. Администратор может разрешить клиенту ввод веса с отдельных весов или этикетки. Подключённых весов и проверки веса в приложении нет. Фасованные товары можно продавать поштучно. Штрихкоды, камера-сканер, маркировка и складской учёт не входят в первую версию.

## Доступы

| Роль | Возможности |
|---|---|
| Клиент | Каталог, корзина, оформление заказа, оплата и просмотр текущего заказа |
| Продавец | Оплаченные заказы к сборке, выдача, история, оформление продажи; проверка ручной оплаты |
| Администратор | Всё выше, товары и цены, настройка точки и оплаты, статистика, копии и PIN-коды |

Права проверяются в слое базы, а не только наличием кнопок. PIN-коды хранятся в виде PBKDF2-хешей с индивидуальной солью. После пяти неверных попыток вход блокируется на пять минут. После перезапуска приложение открывается в режиме клиента. Доступ сотрудника закрывается после трёх минут без действий или минуты в другом приложении.

## Оплата

### Полностью самостоятельная оплата: Сбер СБП

Нужен **договор интернет-эквайринга Сбера с включённым СБП и API-доступ к шлюзу ecommerce**. Это отдельный банковский продукт: обычный пароль СберБизнес и наличие POS-терминала сами по себе не дают API-доступ.

1. Получите у банка API-логин, API-пароль и согласуйте HTTPS-ссылку возврата.
2. Администратор → «Автоматическая оплата · Сбер СБП». Сначала используйте тестовые банковские данные и тестовый шлюз.
3. Сохраните подключение: СБП включится автоматически. Для автономного сценария в «Точка и оплата» оставьте этот способ единственным.
4. Клиент оформляет заказ. Приложение создаёт банковский платёж с точной суммой и показывает банковскую страницу. На планшете покупатель сканирует QR своим телефоном.
5. Приложение опрашивает банк. Продажа подтверждается только при совпадении номера заказа, суммы и валюты и полном получении средств. Переход на ссылку возврата не считается оплатой.

API-данные шифруются ключом Android Keystore, остаются на устройстве торговой точки и не попадают в копию или исходники. Приложение предназначено для **устройства владельца точки**, а не распространения покупателям с API-данными магазина. Банк должен разрешить выбранный способ интеграции для вашего договора. Доверие TLS не отключается; при ошибке сертификата проверьте дату устройства и официальные требования банка к сертификатам.

Тестовый шлюз помечается на экране заказа. Его операции исключаются из выручки и рейтинга товаров. После потери связи открывайте тот же заказ и проверяйте статус; не создавайте новую покупку для повторной оплаты. Идентификатор платежа сохраняется в базе. Возвраты ранее подтверждённых платежей выполняются отдельно в банке; приложение не ведёт учёт возвратов.

**Живая банковская интеграция ещё не проверена:** контрактные тесты включены в проект, но реальные банковские доступы не предоставлялись. Перед использованием нужны проверка на тестовом шлюзе и контрольная операция по правилам банка. Официальная [документация API Сбера](https://ecomtest.sberbank.ru/doc) и [описание регистрации заказов](https://developers.sber.ru/docs/ru/sberpay-sdk/signup/sign-up-ecom).

### Наличные, статический QR и отдельный терминал

Эти способы работают **с проверкой продавцом**. Для СБП загрузите изображение QR торговой точки или HTTPS-ссылку от банка. При статическом QR клиент вводит сумму сам; продавец проверяет поступление в банковском приложении. Кнопка открытия установленного платёжного приложения лишь открывает его, результат автоматически не получает.

Автоматическая работа физического POS-терминала Сбера через UPOS требует отдельного адаптера, совместимого оборудования и SDK банка. Она **не реализована**. [Официальный SDK UPOS для Android](https://developers.sber.ru/docs/ru/upos/android).

Само приложение бесплатно. Эквайринг и СБП оплачиваются по условиям вашего банка.

## Товары, статистика, копии

До 100 позиций: название, цена, штуки / килограммы, показ или скрытие. Скрытый товар сохраняется в старых заказах. Суммы хранятся в целых копейках, вес — в граммах; сумма весовой позиции округляется до копейки. Заказ сохраняет свои цены и названия при последующем редактировании каталога.

Статистика: число подтверждённых продаж, выручка, средняя покупка, пять популярных позиций за сегодня, последние семь календарных дней или всё время. Популярность считается по числу заказов с товаром. Это учёт продаж, без расходов, прибыли и возвратов.

Администратор может сохранить JSON-копию через стандартный выбор файла Android. В ней товары, настройки, заказы и идентификаторы банковских платежей; PIN-кодов и API-паролей нет. Восстановление проверяет данные и заменяет их одной транзакцией, оставляя текущие PIN-коды. Автоматическое подключение банка после восстановления нужно настроить заново с тем же банковским аккаунтом. Пока есть незавершённый банковский платёж, заменять базу или менять аккаунт / шлюз нельзя; пароль того же аккаунта можно обновить. Попытки, для которых касса не получила банковский платёж и QR, администратор может снять отдельной кнопкой в настройках банка. Размер импортируемого файла — до 32 МиБ.

Данные и настройки сохраняются между перезапусками. Интернет нужен для банка и банковской страницы; каталог, наличные продажи и статистика работают без него. При потере интернета автоматическая оплата не считается успешной.

## Фискальные чеки

Приложение ведёт заказы и учёт продаж. **Оно не является ККТ, не отправляет данные в ОФД и не формирует фискальные чеки.** Экран «Оплачен» не заменяет фискальный чек. Для использования как полноценной торговой кассы необходимо отдельно обеспечить фискализацию подходящим кассовым оборудованием или сервисом. Проект пока не включает такую интеграцию.

## Для разработки

Java + стандартные Android Views + SQLiteOpenHelper. Нет npm, Gradle, внешних библиотек приложения или собственного сервера. Сборка использует Python 3.10+, JDK 21 и официальные Android SDK Platform 36+ / Build Tools 36+.

Установите инструменты через Android Studio / SDK Manager. Укажите `JAVA_HOME` и `ANDROID_HOME`, затем:

```sh
python scripts/build.py --core-test
python tests/sqlite_check.py
```

Результат: `build/small-pos.apk`. Также можно передать пути явно:

```sh
python scripts/build.py --sdk "путь к Android SDK" --java "путь к JDK" --core-test
```

Первый запуск создаёт ключ подписи в игнорируемой папке `build/signing`. **Сохраните её отдельно и используйте при всех обновлениях**; Android не установит поверх существующего приложения APK с другой подписью. Не выкладывайте ключ и пароль на GitHub. Для переданного с этим проектом APK исходный ключ сохранён отдельно от публичного архива; сборка с новым ключом не сможет обновить его поверх.

```sh
python scripts/build.py --signing-dir "путь к вашему сохранённому ключу" --output release/small-pos.apk
```

Перед обновлением сделайте копию данных. Для следующих релизов увеличивайте `versionCode` и `versionName` в манифесте. Эта первая версия использует схему базы 1; изменение схемы требует явной миграции, без удаления данных.

### Тесты на Android

На **свежем тестовом эмуляторе**, не на устройстве с вашими рабочими данными:

```sh
python scripts/build.py --core-test --tests
adb -s emulator-5554 install -r build/small-pos.apk
adb -s emulator-5554 install -r build/small-pos-tests.apk
adb -s emulator-5554 shell am instrument -w ru.smallpos.tests/ru.smallpos.app.RetailInstrumentation
```

Тесты проверяют настоящую Android SQLite-базу, роли, PIN-коды, сохранение, снимки цен, повторы запросов, вес, копии, пагинацию и ответы банка на тестовых данных. Сценарий интерфейса создаёт тестовую кофейню в основной базе **эмулятора**. Не запускайте его на рабочем устройстве.

В `.github/workflows/android.yml` включены сборка, базовые проверки и Android-тесты на Linux. APK из CI подписывается временным ключом и предназначен для тестирования. Для распространения обновлений собирайте релиз постоянным ключом.
